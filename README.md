# DecodeX

**A technical scavenger hunt conducted entirely inside a GitHub repository.**

DecodeX asks you to treat a repository the way an investigator treats a case
file. The answer is present, but it is distributed. It sits across files,
branches, issues, pull requests, releases, workflow runs, and configuration
entries — and no single view of the repository shows the whole picture.

Your task is to find it, prove where it came from, and explain what connects
the pieces.

## What DecodeX is

DecodeX is a scavenger hunt built on a GitHub repository. Instead of handing
participants a map, the organizers have placed problem statements across the
repository's ordinary surfaces — the kind of place a real project leaves behind
and forgets about.

The hunt is not about writing the fastest code. It is about **observation,
navigation, and verification**: noticing that a filename means something, that a
configuration file points somewhere, that a comment thread carries more than the
description above it, that a workflow communicates through its output rather
than its definition.

### Why GitHub

GitHub is a genuinely difficult search space, and that is the point. A
repository is not one page. It is a versioned, branchable, commentable,
annotatable, automatable object with its own history and metadata. Using it as
the challenge environment means participants practise the same navigation skills
they use on real projects: reading a diff, following a reference, checking a
workflow run, comparing two versions of a document.

### What you are not required to build

**You are not required to develop a complete application during the discovery
phase.** DecodeX measures whether you can find, source, and interpret the
material — not whether you can ship a production system in a few hours. Building
something may help you understand a problem statement, but it is not the
objective, and it is not scored. If organizers later invite teams to build on
their findings, that will be communicated separately.

### Expect deliberate references

The repository contains intentional references. Not every useful detail is
visible from the landing page, and the main page is not a complete index of the
hunt. Treat the repository as an evidence set rather than a document.

## Challenge objective

1. **Explore** the repository and the GitHub features it exposes.
2. **Identify** references, pointers, and clues.
3. **Follow** links and investigate the resources they lead to.
4. **Discover** the hidden problem statements.
5. **Record** the evidence and the source location of each discovery.
6. **Understand** the requirements and key features of what you found.
7. **Present** your findings to the organizers in the manner they prescribe.

Final submission instructions will be communicated by the organizers.

Useful material may appear in any of the following. This is a list of *surfaces*,
not a solution map — and the repository may not use every one of them.

| Surface | What to understand about it |
|---|---|
| **Repository files and folders** | Contents, naming, nesting, and what a file's location implies about its purpose. |
| **Markdown documentation** | Prose, tables, front matter, and links between documents. |
| **Configuration files** | Dotfiles such as `.gitignore`, and other configuration whose *contents* may matter as much as its behaviour. |
| **GitHub Issues** | Both the description and the comment thread. A thread frequently carries information the description omits. |
| **Pull Requests** | Titles, descriptions, diffs, and review or comment discussions. |
| **Releases** | Release notes, which often hold more context than a version number suggests. |
| **GitHub Actions** | Workflow definitions *and* the outputs they generate during a run. |
| **Branches, commits, tags** | History that is not visible from the default branch. |
| **Referenced resources** | Anything a file or configuration entry points to — follow it to its destination. |
| **Repository metadata** | Descriptions, topics, and other metadata where relevant. |

### A clue may be a pointer, not the content

Some entries in this repository exist only to direct you somewhere else. A
comment that reads like housekeeping may be carrying an address. A line in a
configuration file may be a filename. Treat every reference as a link to follow
rather than as an answer in itself — and treat whatever it points to as
something to verify.

## Rules and fair play

### Team rules

- Maximum **4 participants** per team.
- Team members should coordinate their work and share findings.
- Organizers' instructions on team formation and eligibility apply.

### Repository rules

- Participants may inspect publicly available repository content and GitHub features.
- **Do not** delete, modify, overwrite, or damage repository content.
- **Do not** create unrelated issues, pull requests, comments, commits, branches, or releases.
- **Do not** modify existing workflows or trigger unnecessary workflow executions.
- **Do not** attempt to access private resources, restricted accounts, credentials, tokens, or unauthorized systems.
- **Do not** exploit GitHub or use methods that disrupt the platform or the repository.
- **Do not** expose secrets or personal information if encountered.
- Respect GitHub's terms and the organizers' instructions.

### Fair-play rules

- **Do not** impersonate other teams or participants.
- **Do not** intentionally obstruct another team's exploration.
- **Do not** claim an unverified guess as a confirmed discovery.
- **Preserve evidence** of discoveries, including relevant URLs or screenshots where permitted.
- Follow the organizers' instructions regarding evaluation and final decisions.

## Evidence and discovery record

Keeping a structured log is the single highest-value habit in this hunt. If a
discovery is not sourced, it is not a discovery.

| Field | What to record |
|---|---|
| **Discovery** | Name or short description of the finding |
| **Source** | GitHub feature or repository resource |
| **Reference** | URL or path to the source |
| **Evidence** | Relevant excerpt, screenshot, or explanation |
| **Connection** | How the clue led to the discovery |

> **Note**
> This is a recommended way to organise your findings, not an official submission
> form. Follow the organizers' instructions for the format they require.

## Tips for participants

- **Read carefully before concluding.** The difference between "probably" and "confirmed" is worth more than a fast answer.
- **Follow every reference.** If something points at a location, go there.
- **Check comments and discussions**, not just main descriptions.
- **Notice filenames and configuration entries.** A name is often a deliberate signal.
- **Compare information across locations.** Contradictions between two sources are usually intentional.
- **Keep a discovery log** as you go, not afterwards.
- **Verify completeness.** Before recording a problem statement as solved, confirm you have the whole thing — title, theme, difficulty, description, and key features together.
- **Do not assume the default branch holds everything.**
